Resync to the start of a VoSPI segment, not just any valid packet

A wedged unit was rejecting every frame it received. Instrumented counters
read over SWD while the fault was held open with a hanging ffmpeg grab:

    vsync_irqs        +1170     sensor alive, data arriving
    transfers_done    +1170     every transfer completed
    transfer_fails        0     none reported an error
    desync_events     +1170     every single frame rejected
    resync_entries     +390     exactly 1170/3, matching the gate
    resync_packets   +27290     70.0 discard packets per resync, every time
    frames_completed      0     nothing published in 89 seconds

So the sensor was healthy and the firmware was refusing all of its output.
The rejecting comparison is:

    last_end_line != (IMAGE_NUM_LINES + g_telemetry_num_lines - 1)

On the wedged unit last_end_line read 0xFF, with g_telemetry_num_lines at 0,
so it expected 59 and saw 255. 0xFF is not an off-by-one - it is an idle SPI
bus, MISO floating high. Meanwhile current_segment, read from line 20 of the
same buffer, was a perfectly valid 1. Real packets at the front of the
buffer, nothing at the back: the read was running off the end of the data.

The cause is in the resync loop. It discarded packets until the first
non-discard one and then read the remainder of the frame. But VoSPI only
guarantees alignment from packet 0, and "not a discard packet" is a much
weaker condition than "packet 0". Stopping mid-segment left the following
bulk read to run past the segment end into the inter-segment gap, filling the
tail of the buffer with 0xFF. That frame then failed validation and triggered
another resync, which made the same mistake. Nothing short of a power cycle
broke the cycle, because nothing in the loop ever re-established where a
segment actually starts.

Three changes:

- The resync loop now discards until it sees packet 0 of a segment, testing
  the packet number as well as the discard bits.

- That loop is bounded. Requiring packet 0 is a stricter condition than
  before, so it could otherwise spin indefinitely against a sensor that never
  presents one. Hitting the cap counts a giveup and returns to the outer loop
  to retry.

- Frame validation now checks the first packet as well as the last. A
  misaligned read produces plausible early lines and a bad tail, so testing
  only the last line let it get 59 lines further than it should before
  anything noticed. The new check reuses the existing desync path rather than
  failing the transfer outright, so recovery goes through machinery that is
  already known to work.

complete_lepton_transfer() is deliberately left alone. It still returns its
argument's status with a TODO where validation belongs, which is why
transfer_fails stayed at zero across 47,000 transfers, but making it fail
here would route misaligned frames down a path that drops them without ever
incrementing current_frame_count - and the resync gate depends on that
counter, so the firmware would never resync at all. Worth fixing separately.
