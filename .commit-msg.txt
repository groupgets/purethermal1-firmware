Re-initialise the sensor after a bounded run of rejected frames

Losing VoSPI alignment is recoverable. Staying lost was not, and nothing in
the firmware bounded how long it would keep trying: a wedged unit sat in the
resync path rejecting 1170 frames out of 1170 and needed the user to
physically unplug the camera.

This adds the missing bound. Consecutive rejected frames are counted, and past
LEPTON_MAX_CONSECUTIVE_DESYNCS the firmware stops re-reading the stream and
re-initialises the sensor instead: OEM power down, settle, power up, restore
the VSYNC configuration, re-apply the format configuration, clear any stale
EXTI state, and resume. Roughly half a second, against a failure that
previously lasted until someone walked over to the hardware.

The threshold is 60. One rejected frame per stream restart is normal - the
sensor has just been power-cycled and the first VSYNC-triggered read lands
wherever it lands, which is why first_line_bad tracks the grab count almost
exactly during healthy operation. 60 sits an order of magnitude above that and
is reached in two to five seconds when something is genuinely stuck.
g_dbg.worst_desync_run now records the longest run actually observed, so the
threshold can be tuned from measurement rather than from my guess.

Deliberately indifferent to root cause. Two real defects have been found and
fixed so far - an EXTI pending-bit clear that passed an IRQ number where a pin
mask belonged, and a VSYNC phase delay that was only ever set at boot despite
the sensor being power-cycled on every grab - and either could have been the
whole story, or neither. This commit does not care. Whatever leaves the
pipeline unable to produce a frame, recovering in half a second beats
requiring a human with a USB cable.

The format configuration is factored into apply_format_config() and called
from both the stream-restart path and the recovery path, so the two cannot
drift apart. The recovery waits use PT_WAIT_UNTIL rather than HAL_Delay, so
usb_task keeps running and the device stays enumerated throughout.

Two new counters: hard_recoveries counts how often this fires, which should be
zero in normal use and is the number to watch in a soak; worst_desync_run
gives the headroom between normal operation and the threshold.
