Restore the Lepton VSYNC phase delay after every power cycle

VSYNC is how the firmware learns a VoSPI segment is ready, and
LEP_OEM_VSYNC_DELAY_PLUS_2 is what aligns that pulse with packet 0 of the
segment. Both were set exactly once, from set_lepton_type(), reached only
through init_lepton_command_interface() at main.c:177 during boot.

But lepton_task() OEM power-cycles the sensor on every stream teardown and
restart: lepton_low_power() on the way down, lepton_power_on() on the way
back up, once per frame grab. OEM GPIO configuration does not reliably
survive that, and nothing ever put it back.

When the phase delay reverts, the failure is quiet. VSYNC still fires, so the
interrupt still arrives, transfers still complete, and the sensor looks
entirely healthy from every angle we had been measuring. What changes is that
the pulse no longer coincides with packet 0, so every VSYNC-triggered read
starts somewhere in the middle of a segment, runs off the end into the
inter-segment gap, and fills the tail of the buffer with 0xFF.

The measurement that isolated it, taken on a wedged unit with the fault held
open by a hanging ffmpeg grab:

    resync_giveups      3        static
    first_line_bad   1817        climbing

The resync loop walks the stream packet by packet and never consults VSYNC.
It found packet 0 every time - giveups stayed flat. The VSYNC-triggered bulk
read never did. Alignment was recoverable by reading, and un-recoverable by
waiting for VSYNC, which puts the fault squarely in the VSYNC-to-packet-0
relationship. The phase delay is the only thing that governs it, and it was
last written at boot.

That also accounts for the symptoms that defeated the earlier attempts. It
survives a USB re-enumeration, because re-enumeration does not reset the
STM32 and the STM32 is not what lost the setting. Only removing power fixes
it, because only a reboot runs set_lepton_type() again. It fires
probabilistically per teardown, because whether a given OEM power cycle
clobbers the register is not deterministic. And it is invisible to every
health check we ran, because nothing downstream of VSYNC is broken.

lepton_restore_vsync_config() is now called after each lepton_power_on() in
the stream restart path, and set_lepton_type() calls the same function so
there is one place that knows what the correct configuration is. Failures are
counted in g_dbg.vsync_cfg_fails rather than discarded, since a silent
failure here is precisely how this went unnoticed.
